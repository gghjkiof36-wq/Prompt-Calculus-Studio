# Danbooru 詞庫與 Tag 自動補全：可行性及接入提案

> 2026-09-10 更新：目前採按需聯網候選、本地快取與工作區常用排序，沒有全量詞庫下载。中文字典可編輯，Google Cloud 接口已準備但尚未以實際金鑰測試。以下全量抓取／匯入內容保留為早期提案；操作以 [README.md](../../../README.md) 為準。

日期：2026-09-09。

依使用者本輪補充，英文 Tag 自動補全、完整 Danbooru 詞庫及繪師標籤的優先度高於翻譯。本文件補充 DESIGN.md；原先將所有 Dictionary 功能延到第二階段的安排，調整為「先加入英文補全與詞庫來源，中文自然語言翻譯仍延後」。

## 已確認可行的部分

本輪使用 Python 標準函式庫對 Danbooru 官方公開 API 做了五次小量、唯讀查詢，全部取得 HTTP 200；沒有登入、下載圖片或抓取完整資料庫。

| 查詢 | 實際回傳中的例子 |
|---|---|
| 名稱前綴 `simple*` | `simple_background`、`simple_bird`、`simple_fish` |
| 名稱前綴 `ap*` | `apron`、`apple`、`apex_legends`、`applying_makeup` |
| 名稱前綴 `ap*`，category = 1 | `apple_caramel`、`apios`、`aposine` |
| 有效 Tag Alias | 取得 antecedent_name、consequent_name、status |
| 不限名稱、依 ID 倒序的標籤頁 | 取得包含新繪師及角色的紀錄 |

繪師篩選測試送的是 `ap*` 加上 category = 1；`@ap` 是本工具可以提供的輸入操作，並非聲稱 Danbooru API 原生接受這種前綴。

實測結果保存在 [research/danbooru-probe-result.json](../../../research/danbooru-probe-result.json)，小量驗證程式是 [research/danbooru_probe.py](../../../research/danbooru_probe.py)。查詢結果、使用次數及名稱會隨網站更新。

最初 Windows HTTP 用戶端發生 TLS 錯誤；改用 Python 標準函式庫後成功，沒有關閉憑證驗證。因此已有可工作的 Python 連線路徑，不把前一個用戶端的失敗當成 Danbooru 不支援。

## 官方提供哪些基礎能力

- `/tags.json` 提供標籤名稱、分類、post_count、是否棄用等欄位，支援名稱／別名搜尋及使用次數排序。Artist 的 category 是 1；一般、作品、角色、Meta 也各有分類。[Danbooru Tags API](https://safebooru.donmai.us/wiki_pages/api:tags)
- `/tag_aliases.json` 提供別名、正式名稱與有效狀態，可用於把舊拼法查到目前標籤。[Danbooru Tag Aliases API](https://safebooru.donmai.us/wiki_pages/api:tag_aliases)
- 一般 API 支援 ID 游標分頁；標籤這類端點每頁上限 1,000 筆。官方建議持續讀取時約每秒一次，不能讓每次按鍵觸發全站查詢或大量並行下載。[Danbooru API 文件](https://safebooru.donmai.us/wiki_pages/help:api)
- 網站也有 `/autocomplete.json` 服務；原始碼呈現名稱／別名、詞組、部分非英文其他名稱及拼字補正的處理方式。但我們不需要完全複製網站的排序，個人常用順序可以在本機完成。[官方 Autocomplete 原始碼](https://github.com/danbooru/danbooru/blob/master/app/logical/autocomplete_service.rb)

## 接入方式提案

候選的來源是 Danbooru 收錄的詞庫，不限使用者已收藏的 Prompt Item。資料來源與儲存位置分開考慮：從 Danbooru 匯入後存到 SQLite，仍是 Danbooru 詞庫，只是使用時可以離線搜尋。

### 優先路徑：完整公開詞庫的本機副本

1. 透過官方 Tags API 分頁取得資料，包含繪師、角色、作品、一般與 Meta，不以熱門程度刪除冷門詞。
2. 另同步 Tag Alias 的對照及有效狀態；候選別名預設使用 active 關係，其他狀態保留來源資訊，不誤當成正式替換。
3. 在暫存資料區建立索引，檢查紀錄及引用後，才切換到新版本。
4. 日常輸入只查本機索引，視窗中僅顯示少量候選；使用者可以主動更新詞庫。
5. 另保留詞庫檔匯入途徑，能搬到離線電腦使用；第三方檔案必須標出來源、日期、分類範圍和篩選條件，不能把熱門詞精簡包叫作全量。

「完整」應指同步時公開可取得的詞庫及明確的收錄範圍。網站持續更新，分頁取得也不是伺服器同一瞬間的原子快照，不能保證永久涵蓋所有新增、刪除、改名或不可公開取得的紀錄。需要記錄同步開始／完成時間、最後成功 ID、分類數量及是否有失敗頁。

本輪沒有跑完整同步，因此尚未知道實際總筆數、完整下載時間、最終 SQLite 體積，以及空使用次數／棄用紀錄在全量取得中的覆蓋情形。這些要用完整同步驗證；不以最大的 Tag ID 當成標籤總數，也不先承諾百分之百覆蓋。

同步採可取消、可續傳的背景工作；碰到限流依回應退避，失敗不換掉仍可用的舊詞庫。增量新增可參考 ID 游標，但更新既有名稱／分類／使用次數還需要修改時間及定期對帳，不能只抓新 ID 就稱為完整更新。

目前沒有確認到可直接匿名下載、未經篩選且保持更新的官方單檔全量包，因此不把「官方 CSV 一鍵下載」當成已存在的功能。官方 API 分頁是已找到的可行取得路徑；若後續確認可靠資料匯出包，再替換首次資料來源即可。

### 額外路徑：線上補查

可提供「查詢 Danbooru 最新結果」入口，用相同的輸入前綴直接查官方 API，並在回傳後以使用者常用資料重新排序。這適合找尚未收錄在本機快照的新詞。

線上查詢與本機查詢使用同一套候選資料格式。若之後採自動線上補查，需合併重複請求、快取結果、限制頻率，且過時回應不能覆蓋新的輸入；無網路時繼續使用已有詞庫。線上功能是否預設開啟仍屬提案，核心離線功能維持不變。

## 在介面中的行為

- 自動補全放在「新增／編輯 Item 的 Prompt 欄位」與「最終 Prompt 編輯框」。原有素材庫搜尋框繼續用來搜尋已保存的組合，不把兩種搜尋混成一張長清單。
- 輸入 `simple`，游標附近出現候選，例如 `simple_background`；以滑鼠點選或方向鍵＋Enter／Tab 接受，Esc 關閉。
- 候選列以 Tag 名稱為主，旁邊放分類和簡短的「常用／Danbooru」來源提示，預設約 8–12 項，避免占滿主畫面。
- 僅替換游標所在的待補全部分，不替換整段 Prompt；要正確處理逗號、括號、跳脫字元、權重與 `<lora:...>`。無法可靠判定邊界時不擅自補寫。
- 點選候選就能立即使用，不要求先存成 Item。需要收藏成一個 Prompt 組合時，再使用現有「存入素材庫」。
- 對最終輸出的任何候選插入都算手動修改，沿用已確認的手動稿保留規則。
- 中文輸入法組字期間不攔截 Enter；選完字後再處理查詢。

本輪尚未修改互動原型或建立 Qt 補全視窗，以上是下一步接入設計。

## 繪師、`@` 與模型文字格式

Danbooru 的 category = 1 能直接區分繪師標籤，無須從名稱猜測。因此工具可以把使用者輸入的 `@ap` 解析為「查詢 ap 開頭的繪師」，候選插入時保留使用者需要的 `@`。

`@` 同時涉及模型的實際 Prompt 語法，不能一律當成 UI 控制符剝除。Anima 目前官方說明要求繪師前加 `@`；一般 Tag 建議使用空格而非底線，score Tag 是底線例外。[Anima 官方模型說明](https://huggingface.co/circlestone-labs/Anima#prompting)

建議把「字典原始名稱」和「插入文字」分開，並讓工作區選擇輸出格式。例如：

| 原始字典名稱 | 保留原名 | Anima 格式示例 |
|---|---|---|
| `simple_background` | `simple_background` | `simple background` |
| `apple_caramel`，Artist | `apple_caramel` | `@apple caramel` |

這只處理新接受的候選，不批量改寫既有 Item、手動稿或任意自訂文字。工作區的模型格式設定屬本輪新提案，尚未當作既定介面細節。

Danbooru 收錄與模型能否準確表現是兩件需要分別驗證的事；字典不能保證每個繪師／角色都在該模型訓練資料中。Anima 官方另提到部分命名差異偏好 Gelbooru 版本，目前先依使用者要求採 Danbooru，不自動擴成多站合併詞庫。

## 把常用詞排前面

先排除不匹配的候選，再考慮：

1. 名稱或有效別名的完全匹配／前綴匹配品質。
2. 使用者在目前工作區接受過該候選的頻率與最近使用情形。
3. 使用者跨工作區的使用頻率。
4. Danbooru 的 post_count，作為沒有個人記錄時的初始排序依據。

以上為排序提案。候選被真正接受時才記次數，僅出現在清單不計入；這個計數代表工具內的使用習慣，不宣稱讀取了使用者過去所有 ComfyUI Prompt。詞庫更新不得清掉使用者累積的常用資料。

「最適合」在第一版指文字匹配和使用習慣，不是模型對整張圖的語意或風格效果評分。需要進一步排序時可再調整，不引入大型模型。

## 中文與翻譯的安排

使用者已表明翻譯不是剛需，因此英文補全可以先完成。之後可在同一詞庫上疊加自訂中文對照，例如「簡單背景 → simple_background」。

Danbooru 的 Tag Alias 通常是標籤對照，不等於完整中文翻譯。官方補全另會查 Wiki／Artist 的 other_names，可能涵蓋部分非英文名稱，但不能據此宣稱所有標籤都有可靠中文名稱，更不能保證整句中文轉 Prompt。[官方補全的 other_names 處理](https://github.com/danbooru/danbooru/blob/master/app/logical/autocomplete_service.rb)

整句翻譯、中文描述解析或自動創作 Tag 仍留待後續，且不影響離線詞庫與英文補全。

## 資料與性能安排

在 SQLite 增加詞庫來源／版本、標籤、站方別名、使用者中文對照、候選使用記錄等資料；外部詞庫和個人 Prompt Item 邏輯分開，更新詞庫不覆蓋素材。

前綴欄位建立適合查詢的索引，查詢後只取少量結果；不把全量標籤各建立一個 Qt 元件或 Python 常駐物件，不每次按鍵掃描整份 CSV。個人常用查詢和站方熱門查詢分別取候選後合併，避免把曾用但冷門的匹配詞排除在候選池外。

同樣不需要 LLM 或 GPU 推論。初次同步及建立索引會花時間，日常效能需用完整詞庫量測，不能把本次五筆 API 查詢的速度當成全量性能。

## 下一步驗收

1. 全量同步可以續傳，並報告收錄範圍、成功／失敗狀態；不能以中斷下載冒充完整匯入。
2. 輸入 `simple`／`ap` 會出現實際詞庫候選，輸入 `@ap` 只出現 Artist 分類。
3. 滑鼠接受候選後，僅替換當前輸入片段，且保留已有權重、括號、其他文字和手動稿。
4. 多次接受某個符合前綴的詞，能反映在之後的候選順序；重啟後仍保留。
5. 已匯入詞庫時，斷網仍能搜尋並複製；更新失敗仍可使用舊詞庫。
6. 自訂中文對照、非 Danbooru 的 Prompt、繪師 `@` 和不同工作區格式不互相覆蓋。

本輪完成的是「官方能力核實＋實際 Python API 連線驗證＋設計補充」，並未完成完整詞庫下載、自動補全成品或 Windows 封裝。
