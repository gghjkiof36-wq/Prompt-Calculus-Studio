# Documentation evidence

- Describe the fixed version covered by the evidence. A roadmap, old technical contract or visible preview is not proof that a capability is shipped; a source/package hash is not an installation or GPU test.
- Keep current state in the relevant version/status record and link to it. Do not append a new “current” paragraph beneath contradictory old ones without marking the old material historical.
- Public docs must stand alone without local task IDs, private paths, credentials, private reviews or user images. Name the tested version of screenshots and the limits of reported results; do not invent adoption figures or CI badges.

- Write public release notes for users: changes they can use, what to download and how to start, then important known problems with concrete actions. Keep verification procedures, task boundaries, group handoffs and lists of work not performed in their technical records.
- Explain a missing requirement by naming what users need and what it affects. Keep version history in the version table; label licenses in a fixed license section. Do not turn illustrative version examples into release announcements.
- Before editing version text, classify product names, numeric parameters, third-party workflow names and historical observations. Preserve original observed strings with a short mapping where needed; never apply blanket numeric replacement.
